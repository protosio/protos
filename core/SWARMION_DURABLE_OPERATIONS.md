# Durable operations on Swarmion

Swarmion accepts and publishes a successful write locally before checkpointing,
durable materialization, and remote convergence finish. Backend workflows must
therefore use an operation identity and its exact event/root receipt; a Dolt
root alone is not an operation identity.

## Instance-delete recovery

Instance-delete tasks use the `immutable_operation_recovery_v1` recovery model:

1. The queued task contains the complete, JSON-persisted opaque
   `OperationIdentity` and `OperationRecovery`, plus the expected delete
   invariant. The random key is generated by Swarmion; business identifiers
   are binary intent parts under an immutable Protos schema ID.
2. The final business delete and one deterministic `operation_effect` row in
   `task_operation_facts` publish in the same `Execute` request. Seeing that
   fact therefore proves which logical delete produced the SQL state.
3. The validated publication address and exact event/root receipt are recorded
   as a deterministic `published_operation_receipt` fact. Its payload contains
   only event/root and operation/author/intent identity, so every peer using
   the current public receipt contract derives identical content.
4. Task status, progress, owner, timestamps, checkpoint observations, and proof
   results remain mutable projections. They are never part of an immutable
   fact and are not recovery authority.

This removes the post-delete mutable receipt checkpoint (formerly called T92)
from the correctness path. A recovering peer waits for the original operation
binding, observes that exact event through `applied_durably`, verifies that the
atomic effect fact is present, and resumes the projection. It does not publish
another delete.

The receipt fact has one current encoding and is not projected into the mutable
task payload. Recovery resolves the immutable operation and reconstructs mutable
observations from the exact receipt instead of trusting task progress state.

`recovery_version: 1`, the fact kinds, fact-row identity domain, delete
operation schema `io.protos.instances.delete/v1`, and peer-drain authorization
schema `io.protos.instances.peer-drain-authorize/v1` form a fresh persisted-state
boundary. Preview tasks/facts containing only `operation_key`, `intent_digest`,
and `author_peer_id` used a JSON-array digest framing and do not contain an exact
Swarmion recovery record. They are deliberately rejected when the discriminator
is missing or unknown. They must be rebuilt from a fresh repository (or handled
by a separately audited one-time operator migration); they must never be
silently reinterpreted as the new schema+binary identity, authoritative absence,
or permission to replay a destructive action.
A foreign operation miss is likewise not authoritative absence: no timeout
permits replay. Restore the original author history or perform an explicit,
application-verified operator migration/fence before taking ownership of such a
task.

The `task_operation_facts` table is part of the generated initial schema for new
repositories. Later schema additions use explicit migrations; repositories are
adopted only when their recorded schema matches a supported migration boundary
and otherwise fail closed.

## Receipt and content semantics

- `Commit` proves local acceptance/publication, not checkpointing, durability,
  remote convergence, or an application invariant.
- `pending`, `parked_*`, and foreign `unavailable` must be observed; they never
  authorize republishing. Only the direct `OperationRetryPermitted` disposition
  returned under the live runtime lease authorizes another attempt.
- `applied_durably` proves checkpoint application. It is independent of full
  historical-root coverage. `content_dissent` is a passive, revisitable
  observation: it is not durable success, parking, or a reason to replay an
  operation or start an automatic catch-up loop.
- Destructive workflows must query their business invariant `AS OF` the durable
  checkpoint commit returned for the exact receipt.

For ordinary desired-state writes, task enqueue/progress, app lifecycle, route
configuration, and VM deployment state, use receipt availability instead of
waiting for `applied_durably`:

1. Publish and retain the exact event/root receipt.
2. Passively call `WaitReceipt` with an `OtherPeerRetention` requirement of one
   peer and the `OtherPeerRetained` condition.
3. Report `local_accepted` or `other_peer_available` as distinct stages.

An availability success proves one other peer retained the live event/root
closure. It does not prove a checkpoint, canonical application, content
coverage, quorum, or global convergence. A bounded unavailable result is an
accepted write whose replication is not yet provable; it never authorizes a
replay. Fresh single-peer/bootstrap repositories return at `local_accepted`
without waiting for an impossible second-peer proof. For ordinary unscoped
requests, Swarmion selects the current database-scoped logical peers at each
observation boundary. `EligiblePeerIDs` is that topology snapshot, while
`Peers` contains receipt evidence only and may still be empty for a newly
authored receipt. `NoCurrentEligiblePeers` is the explicit weak single-peer
outcome; it is not other-peer availability and grants no replay or destructive
workflow authority. Use stable `ReasonCode` values for control flow, never the
diagnostic `Reason` prose. Pass explicit `PeerIDs` only for intentionally fixed
application-owned replication targets.

Migrations and provider deletion remain explicit exceptions. Migrations consume
a checkpoint snapshot. Provider deletion keeps immutable authorization `P` and
final deletion `D` on exact `applied_durably` receipts with their `AS OF`
business-invariant checks.

Use Swarmion's opaque `OperationRecovery` with `ResolveOperation` or
`WaitOperation`, and use `ObserveReceipt`/`WaitReceipt` with a caller-owned
deadline. These APIs do not hold the SQL workspace while waiting.

## Process recovery journal

Before every `Execute`, including ordinary SQL writes whose random identity is
otherwise hidden from the caller, Protos crash-durably records the complete
opaque identity and receipt-less recovery address under
`.swarmion/protos-operation-recovery`. The write syncs the replacement file,
the journal directory, and every directory created on the first path creation
up to the existing repository parent. A successful call may later enrich that
record with an expected receipt, but concurrent receipt-less writes cannot
regress it. Journal replacement is serialized and requires exact identity,
namespace, author, and branch correlation.

The journal persists recovery evidence, never `OperationRetryPermitted` or a
derived retry decision. On restart, absence retires the record without running
SQL, inconclusive evidence is retained fail-closed, and exact accepted evidence
permits the database to become ready without replaying the SQL body or waiting
for checkpointing. The accepted record remains until lifecycle-owned background
cleanup observes that exact receipt at `applied_durably`; database close joins
that cleanup, and a timeout or close leaves the record for the next restart.
Accepted evidence still dominates a failure to perform the optional post-accept
enrichment: the exact accepted receipt is returned to the caller and the
receipt-less recovery record remains available for restart resolution.

## Peer-drain runtime ownership

Peer-drain finalization, authorization `P`, provider destruction, and deletion
`D` are bound to one captured database-runtime generation. Closing or replacing
that runtime after finalization revokes the continuation; a new runtime cannot
inherit the old generation's absence proof. `P` and `D` revalidate the captured
generation at the private execution boundary before preparing SQL or calling
`Execute`. Each synchronous provider mutation runs only while `D` is resolved
as absent on that same owner, and database close joins an in-flight mutation
before replacing the runtime. The final D transaction atomically deletes peer,
app, instance, and command rows and inserts its immutable effect fact; there is
no earlier standalone app-row deletion.

## Migration catalog identity framing

The immutable migration schema identifier is
`io.protos.migrations.batch/v1`. Its operation key is random and persisted; it
is never derived from a filename, repository, or migration count. The schema
has exactly one binary intent part, so catalog size cannot exhaust Swarmion's
intent-part count as more migration files are added.

That part is encoded byte-for-byte as:

1. ASCII `PROTOS-MIGRATION-CATALOG` (24 bytes).
2. One `0x00` separator byte.
3. One framing-version byte, currently `0x01`.
4. The file count as an unsigned 32-bit big-endian integer.
5. For each filename in bytewise Go string sort order: its byte length as an
   unsigned 32-bit big-endian integer, the filename bytes without a terminator,
   and the raw 32-byte SHA-256 digest of the complete migration file contents.

A zero-file catalog has a zero count and no entries. An empty filename would
have a zero length and is distinct from a zero-file catalog, although migration
discovery rejects invalid paths before publication. Checksums are provenance
only; neither the framing nor its digest encrypts migration contents or provides
confidentiality. Swarmion's operation-identity input bounds remain the outer
limit for the resulting single part.

## SQL adapter expectations

The public runtime does not expose a mutable `*sql.DB`. `QuerySQL` returns
buffered rows for scoped reads, and the backend uses Swarmion's public
`runtime/sqlread` connector. Every mutation enters `DatabaseRuntime.Execute`
with an immutable `OperationIdentity`; its opaque `OperationResult` disposition
is the only retry/publication authority.

An accepted or recorded no-change result consumes the stable identity and
carries an exact receipt; a replay resolves that same operation and does not
rerun the SQL body. `OperationRetryPermitted` is immediate call evidence only
and is never serialized. Recovery-required, failed-closed, unknown, zero, and
terminal results remain non-authorizing. Diagnostics are logged only and are
never searched for authority.

## Dependency updates

Swarmion's public packages are consumed from one root module revision. Validate
the selected module graph with `GOWORK=off`; downstream `replace` directives
are not part of the supported installation path.
